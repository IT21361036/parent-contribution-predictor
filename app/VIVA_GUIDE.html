1The 60-second answer

If the examiner opens with "tell me about your project", this is the whole thing in one breath:

Say this

"This is a role-based Learning Management System for Sri Lankan O/L students with three portals — admin, parent and child. On top of the LMS sit two intelligence layers: an explainable Random Forest that predicts each student's performance risk as low, medium or high with reasons attached, and a transparent Parental Engagement Index formula scoring how involved each parent is.

The contribution is not the finding that parental involvement matters — that's already established. It's the measurement method: a webcam pointed at the parent, verifying in-browser that they're genuinely attending to their child's progress, replacing self-reported involvement with an objective signal. That makes it Multimodal Learning Analytics applied to a new subject.

One model was trained by us. One pre-trained model is used as-is for the camera. One scorer is a deliberate formula, not machine learning."

2Research positioning

2.1 Field vs methodology — keep these separate

  • Field: Learning Analytics → Educational Data Mining → Multimodal Learning Analytics (MMLA). It becomes MMLA the moment camera data joins the behavioural logs.
  • Methodology: Design Science Research (DSR) — build an artifact, then evaluate it.

Examiners notice when a candidate confuses the two. The field is what you contribute to; the methodology is how you did the work.

2.2 The gap

The parental-involvement → performance link is already well established. Claiming to discover it would be a mistake examiners will catch. The defensible novelty is:

The contribution

Objective, camera-verified measurement of parental attention, instead of unreliable self-reports.

Every existing attention study points the camera at the student. No existing work points it at the parent. That absence is the gap.

2.3 Association, never causation

The training data is simulated, so this demonstrates the method and pipeline, not a proven effect size. Always say "associated with", never "causes". The admin Insights page prints this on screen beside the correlation figure — a deliberate honesty guard.

2.4 Ethical stance

  • Privacy-first camera — video processed in-browser; only a number and a duration stored; no frame leaves the device.
  • No self-fulfilling labels — the child never sees their own risk score.
  • Support, not blame — supportive language in all parent-facing risk copy.
  • Minors + webcam — real data collection would require formal ethics-committee review.

4The database

18 tables, 4 enum types, RLS enabled on all 18, 6 policies, 3 indexes, the pgcrypto extension, and 2 private storage buckets.

4.1 The golden rule — know this cold

RLS-vs-API

RLS is enabled on every table, so nothing is world-readable. But all authorization runs in FastAPI using the service-role key, which bypasses RLS entirely. Sensitive tables have RLS on and deliberately no policy — reachable only through the API, which applies its own role and ownership checks. A few harmless reads (own profile, own links, subjects, materials) have policies and go direct to Supabase.

If asked "why not just use RLS for everything?" — RLS cannot express the rules this system needs: "a parent may read this child only if a parent_child_link row exists, and only these columns, and only if the quiz is fully graded." That logic belongs in application code where it is testable. Doing both would create two sources of truth that can silently disagree.

5The backend

FastAPI — 54 endpoints across 14 routers: parent 10, admin 7, quizzes 7, report_cards 6, students 6, materials 3, notifications 3, subjects 3, activity/engagement/predictions 2 each, analytics/health/profiles 1 each.

5.1 Authentication

The browser sends Authorization: Bearer <supabase-jwt>. The backend verifies it against Supabase's JWKS endpoint using asymmetric keys (ES256/RS256), with audience="authenticated" and leeway=10s for clock skew.

Key design point

The role is read from the profiles table, not from the JWT. The token proves who you are; the database is the source of truth for what you may do. Revoking a role therefore takes effect on the next request, not when the token expires.

5.2 Authorization — two independent layers

  1. Role guard — require_role("admin") → 403 if the role doesn't match.
  2. Ownership guard — a parent endpoint additionally verifies a parent_child_link row for that exact child → 403 "Not linked to this child".

Role alone is never sufficient. Being a parent does not grant access to every child, only to linked ones.

5.3 Per-student optional subjects

O/L students take ~6 compulsory subjects plus their own electives. subjects.is_core marks core subjects (implicit for everyone); child_subjects records each student's electives. One resolver — app/services/subject_access.py — answers "which subject ids may this child see" as core ∪ assigned, and every child-reachable read calls it.

Worth mentioning unprompted

Two endpoints had no subject check at all before this: GET /materials/{id}/download and POST /quizzes/{id}/attempts. The second matters most — an attempt on a subject the student doesn't take would pollute their score history and the predictor's features. Finding and closing that is a good thing to volunteer.

5.4 Notification service

Four event types — quiz_result, quiz_due, report_card, risk_alert — fanned out to all linked parents, created only by the backend. quiz_due reminders generate lazily on request with dedup, so no cron job is needed. notify_safe guarantees a notification failure never fails the underlying action. Reading a notification raises check_frequency → raises the PEI — a feedback loop needing no retrain.

6The machine-learning system

Core contribution

Sections 6–9 are the heart of the viva. Know them cold.

6.1 Problem framing

Supervised multi-class classification. Input: 9 numeric features describing one student. Output: one of three risk bands — low, medium, high.

Framed as classification rather than regression deliberately: a teacher acts on "this student needs attention", not on "predicted score 61.4".

6.3 What a Random Forest is — explain it simply

Say this if asked to explain the algorithm

"A decision tree asks a chain of yes/no questions — 'is attendance below 70%?', 'is the quiz average below 0.5?' — and lands on a prediction. A single tree overfits: it memorises its training data. A Random Forest trains 300 trees, each on a random bootstrap sample of rows, considering a random subset of features at each split. Every tree votes; the majority wins. The randomness makes individual trees' errors uncorrelated, so they cancel out — that's bagging, bootstrap aggregation. And because I can count how much each feature reduced impurity across all 300 trees, I get feature importances for free. That's what makes it explainable."

6.5 Where the training data comes from

Why simulate? No public dataset holds this exact combination of features per O/L student — particularly not parental monitoring hours and camera-verified attention, which don't exist in any published dataset because nobody has collected them.

What was done instead: public datasets were mined for their documented relationships, which were then reproduced in a simulated Sri Lankan O/L dataset in our schema.

  • xAPI-Edu-Data (480 rows) — primary grounding; carries real parental fields. Survey answered yes vs no shows a 1.32 / 0.66 split; absences under-7 vs over-7 shows 1.44 / 0.41.
  • UCI Student Performance — family-context features.
  • OULAD — large behavioural reference.

Procedure (seed 42): a latent "engaged household + able student" factor drives correlated features, so columns aren't independent noise. A weighted success score — prior grades 0.24, quiz average 0.20, attendance 0.15, parental ~0.30 combined — plus noise maps to a band: ≥0.60 low, ≥0.42 medium, else high. Every row carries a data_source tag; 480 real xAPI rows are recast into the schema beside 1,200 simulated ones.

Be honest about this

The model learns relationships that were partly designed in. It validates the pipeline — feature contract, training, serving, explanation — not a real-world effect size.

7.3 Models 2 & 3 — the benchmarks (trained, never shipped)

Logistic Regression and Gradient Boosting exist only inside _candidates() in train_predictor.py. Every training run fits all three on the identical split and evaluates them identically.

  • They never touch production. No router imports them; no .pkl is saved for them. Only the winner is serialised.
  • Their results are permanently recorded in predictor_v1.meta.json under all_model_metrics — so the comparison is auditable long after the run, not just a number in a report.
  • Logistic Regression alone gets a StandardScaler in its pipeline, so a linear model competes fairly rather than being hobbled by unscaled features. The two tree models need no scaling.
Why keep benchmarks at all?

Without them, "I chose Random Forest" is an assertion. With them, it is a measured decision with the losing numbers still on record — including the inconvenient fact that they were competitive. That is the difference between a claim and evidence.

7.8 Questions on the model inventory

How many models does your system use?

Five components, one of which I trained. The Random Forest risk predictor is my trained model. Logistic Regression and Gradient Boosting were trained only as benchmarks and are never served. MediaPipe's FaceLandmarker is pre-trained and used exactly as shipped, in the browser. The Parental Engagement Index is a weighted formula, not machine learning. A sixth — an attention-quality classifier — was scoped in my positioning document and deliberately dropped.

Which model powers the parent's engagement score?

None — that's the PEI, a transparent weighted formula: 0.4 × normalised monitoring hours + 0.3 × normalised check frequency + 0.3 × attention. Deliberately not a model, because there's no ground truth for "true engagement" to train against, and a parent being scored deserves to see exactly why.

Which model runs in the browser and which on the server?

MediaPipe runs entirely in the browser on the parent's own device — that's the privacy backbone, since no video ever reaches my server. The Random Forest runs server-side in FastAPI, loaded once from a pickle and cached. The PEI is also server-side. Nothing needs a GPU anywhere.

Did you fine-tune MediaPipe?

No — not modified in any way. Fine-tuning would need labelled gaze data that doesn't exist for this task, plus a GPU and weeks of work, and it would gain nothing since MediaPipe's landmarking is already strong. What I built is the rule layer on top: what counts as attentive, blink debouncing, liveness, and the anti-gaming accumulator. MediaPipe gives me 478 coordinates and no concept of attention.

Do you use any NLP or a language model?

No. MCQ answers are graded by exact string comparison against the key; short-answer questions are marked manually by an admin, and the parent notification is deliberately held back until grading completes so no misleading partial score goes out. There is no NLP, no LLM and no text model anywhere in this project.

Where do the three models' comparison numbers live?

In predictor_v1.meta.json, under all_model_metrics — all three models' accuracy, precision, recall, macro-F1 and cross-validated F1 are written at training time and surfaced in the admin model-health view. The comparison stays auditable rather than existing only in a report.

Your positioning document mentions an optional attention-quality classifier. Why didn't you build it?

It was flagged optional from the start, contingent on scope. It would have needed a proxy dataset like DAiSEE and added a second trained model without strengthening the core contribution — which is measuring whether a parent is attending, not classifying how well. Delivering the planned scope fully was the better engineering decision than half-delivering a wider one, and my positioning document said so before I started.

If MediaPipe loads from a CDN, does your camera work offline?

Not on first use — the WASM runtime and the model file are fetched from external CDNs, then cached by the browser. Afterwards it works offline. For a guaranteed-offline deployment I'd self-host both assets, which is a build-config change rather than a code change. Everything else in the app runs fully offline against a local backend.

7.7 Why parental_attention ends up least important — the real reason

Correcting a common mis-statement

It is often said that this feature is unimportant "because it was constant". That is only half true, and an examiner who reads the generator will catch it. In the 1,200 simulated rows it does vary. It is constant at 0.5 only in the 480 recast xAPI rows.

The accurate explanation has three parts, and it is stronger than the simple version:

  1. Compressed variance by design. In simulation it spans only ~0.325–0.675, while prior_avg_score spans 35–90. Trees split on thresholds, so a feature with a narrow range offers fewer discriminating cut-points and yields less impurity reduction — regardless of its true relationship to the outcome.
  2. Constant across 28.6% of the data. All 480 xAPI rows carry exactly 0.5, so for more than a quarter of the training set the column provides zero information.
  3. Correlated with stronger features. It is drawn from the same latent factor as everything else. When features are correlated, tree ensembles distribute importance toward whichever one splits most cleanly — here prior_avg_score, with far more spread. The information is present but attributed elsewhere. This is well-known importance dilution under correlated inputs, not evidence of irrelevance.
The defensible conclusion

Its assigned weight in the label formula is 0.10 — fifth of nine, ahead of three other features — yet its measured importance is last at 0.0586. That gap between designed weight and recovered importance is itself the finding: with a low-variance, partly-constant proxy, the signal cannot be recovered. It is precisely the argument for collecting real camera data, where the variance would be genuine. Reporting 0.0586 as evidence the camera doesn't matter would be a misreading of your own experiment.

7.10 Questions on the data

Which datasets did you actually use, and for what?

Two real ones. xAPI-Edu-Data does two jobs: I mine it for the parental-involvement and absence relationships, and I recast all 480 rows into my feature schema as real training data. UCI Student Performance is used only for evidence — correlations between family support, parent education, absences and the final grade — to justify my simulation weights; none of its rows enter training. OULAD is in the repo as background reading but no code loads it. The trainer itself reads exactly one file: the generated 1,680-row CSV.

Why not just train directly on xAPI or UCI?

Neither holds my feature schema. I need per-student parental monitoring hours, check frequency and camera attention alongside quiz and activity data — no public dataset has that combination, because camera-verified parental attention has never been collected. xAPI has coarse parental flags but no numeric time; UCI has family context but no behavioural logs. So I mine both for relationships and reproduce those in my own schema, while still recasting the 480 xAPI rows so real data is present.

How do you know your simulation is realistic?

Three ways. The directions and rough magnitudes come from measured correlations in real data, not intuition. A single latent factor drives all features, so their inter-correlations resemble reality rather than being independent noise. And Gaussian label noise means the boundary isn't cleanly separable — if it were, accuracy would be near 100% instead of 74.5%. That said, "realistic structure" is not "real", which is why every claim is framed as pipeline validation.

Isn't it circular to generate labels from a weighted formula and then have a model learn those weights?

On the simulated rows, yes, partly — and I state it rather than hide it. Three things mitigate it. Label noise of 𝒩(0, 0.07) means the mapping isn't deterministic. The weights are taken from real measured relationships, so the structure isn't invented. And 480 rows — 28.6% — come from real xAPI outcomes that my formula never touched. The honest claim is that this validates the pipeline end to end; proving an effect size needs a real cohort.

How did you avoid data leakage in the xAPI recast?

By construction. Every feature is derived only from behavioural columns — raised hands, visited resources, discussion, absence band, parental flags. The label comes solely from the Class column, which is never used to build any feature. So the outcome cannot leak into the inputs, and it's stated in the function's docstring as a deliberate guard.

Your classes are imbalanced — 706 medium against 339 high. Why no SMOTE or class weighting?

At roughly 2:1 the imbalance is mild, and two choices already address it: the split is stratified so every class is properly represented in both train and test, and macro-F1 is the headline metric, weighting the 339-row class equally with the 706-row one. Resampling adds synthetic rows to data that is already partly synthetic, which would weaken the argument rather than strengthen it. On a real cohort with a rarer high-risk class, class weighting would be my first addition.

Why is parental_attention constant in the xAPI rows?

Because no public dataset contains camera-verified parental attention — it's the signal my project exists to create. For those 480 real rows I use the neutral 0.5 placeholder, the same value production uses when a parent has no webcam. In the simulated rows it does vary, though over a deliberately narrow range. That combination is the main reason it ends up the least-important feature, and I'm careful not to read that as evidence about the real signal.

Can you reproduce your results?

Yes, exactly. Every stochastic step is seeded with 42 — the simulation's latent draw and noise, the train/test split, and the bootstrap sampling in all three models. 7.2 Why not Logistic Regression?

It has the best cross-validated F1, so this needs a real answer, not a dismissal. Three reasons:

  1. It assumes a linear decision boundary in log-odds. The relationships here are plausibly non-linear and interacting — attendance may only matter below a threshold, and parental monitoring may only help when the student is already engaging. A linear model can only capture that if you hand-engineer the interaction terms; a tree finds them automatically.
  2. Its "explainability" is a different, weaker kind here. Coefficients are interpretable only relative to scaled units, and with correlated features (monitoring hours and check frequency move together) individual coefficients become unstable and can even flip sign. Impurity importances degrade more gracefully.
  3. The CV advantage is inside the noise. 0.7504 vs 0.7281 is 0.0223, against a standard deviation of 0.037 — well within one standard deviation, so it is not a reliable ranking.

7.3 Why not Gradient Boosting?

It edges RF on test macro-F1 (0.7540 vs 0.7521 — a gap of 0.0019, roughly one test row). Reasons it wasn't shipped:

  1. The gap is meaningless. 0.0019 on a 420-row test set is well under one sample's worth of difference.
  2. It is the least stable of the three — CV std 0.0427, the highest. Boosting fits sequentially to residuals, so it's more sensitive to noise, which matters when the data is partly simulated.
  3. Boosted importances are harder to defend. Sequential fitting means later trees correct earlier ones, so importance is spread across correlated features in a way that's less intuitive to explain to a non-technical parent or examiner.

7.4 Why not deep learning / a neural network?

  1. Tabular data of this size. 1,680 rows and 9 features. Neural networks need far more data to beat tree ensembles on tabular problems, and the literature is consistent on this. A network here would overfit badly.
  2. Explainability is the entire point. The feature importances are the parental-factor argument. A black box would defeat the research purpose — I'd have a prediction but no thesis.
  3. No structural prior to exploit. Deep learning wins where there's structure to learn — pixels, sequences, language. Nine independent tabular columns have none.

7.5 Why not XGBoost / LightGBM / CatBoost?

Fair question, since the positioning doc mentions XGBoost as an option. Answer: scikit-learn's GradientBoostingClassifier is the same family and was benchmarked — it didn't meaningfully win. Adding XGBoost would introduce a heavier dependency to chase a difference smaller than the noise floor. If the dataset were 100× larger, XGBoost would be the first thing to try.

7.7 Why classification and not regression?

A regressor predicting a numeric score would need a defensible continuous target, and the intervention is categorical anyway — staff triage students into "watch this one" buckets. Three ordered bands match how the output is actually used, and they make the confidence figure meaningful (predict_proba per band). The cost of being wrong is also asymmetric: missing a high-risk student matters more than misjudging a low-risk one, which macro-F1 captures and RMSE would not.

7.8 Why not unsupervised / clustering?

Clustering would find groups but attach no meaning to them, and there'd be nothing to validate against — no accuracy, no F1, no defensible claim that a cluster is "at risk". The whole point is a labelled, evaluable risk prediction.

7.9 Why MediaPipe pre-trained, rather than training a gaze model?

  1. No dataset exists. There is no labelled parent-attention corpus to train on.
  2. Cost. Fine-tuning needs labelled gaze data, a GPU, and weeks unavailable in this scope.
  3. Privacy — the decisive one. MediaPipe runs in the browser. Training our own would mean shipping video to a server, which destroys the entire ethical position and with it the contribution.

What is ours: MediaPipe returns 478 coordinates. Deciding what counts as attentive, how to debounce it, and how to resist gaming is the contribution — rule logic on top of a proven detector.

7.10 Why is the PEI a formula and not a model?

  1. No ground truth. There's no label for "true engagement" to train against — it would be circular to learn it from the very outcomes it's meant to predict.
  2. A right to explanation. A parent being scored deserves to know exactly why. 0.4 × hours + 0.3 × checks + 0.3 × attention is fully auditable.
  3. Falsifiability. A learned scorer feeding a learned predictor would make the parental argument circular and unfalsifiable.

12The Parental Engagement Index

A transparent weighted formula. Not machine learning. Deliberately.

PEI = 0.4 × norm(monitoring_hours, cap 10)
    + 0.3 × norm(check_frequency,  cap 25)
    + 0.3 × parental_attention          (0.5 placeholder until the camera)

norm(v, cap) = clamp(v / cap, 0, 1)          weights sum to 1

check_frequency = history checks + notifications the parent has read.

Why the caps matter

The caps (10 hours, 25 checks) match the ranges the training data was generated in, so a PEI computed at runtime is directly comparable to the parental features the model trained on. Change one without retraining and serving silently drifts from training.

The engagement_index table is both a product surface (the parent sees their score) and the predictor's parental-feature source.

11.1 The pipeline

  1. Consent gate — explains on-device processing, no video stored, liveness, on-air indicator, 3-minute minimum. Nothing starts until accepted.
  2. Face landmarking — MediaPipe Tasks-Vision 0.10.35 FaceLandmarker, 478 points, on a hidden self-view. Detection every 120 ms (~8 fps); React state throttled to 250 ms so rendering never competes with inference.
  3. Liveness first — confirms a real person via blink or head motion before any attention counts. 8-second timeout, retryable. This is what defeats a photograph propped in front of the webcam.
  4. Eyes-on-screen heuristic — attentive only if the iris is centred in both eyes and the head faces forward.
  5. Accumulation with debounce — a 1.5 s grace window so a blink doesn't break the streak; frame gaps capped at 500 ms so a stalled tab can't inflate totals.
  6. Anti-gaming — switching tabs counts as inattentive.
  7. Minimum-time lock — ≥3 minutes of genuine tracking before Stop enables, with a live countdown.
  8. Result POST — only {attentive_seconds, total_seconds, liveness_passed}. No frame ever leaves the browser.

14.1 On the research

What is your actual research contribution?

Why simulated data? Isn't that a weakness?

No public dataset holds this feature combination per O/L student — parental monitoring hours and camera-verified attention don't exist in any published set because nobody has collected them. Isn't your model just learning relationships you designed in?

Partly, yes, and I state that openly. The simulation encodes effect sizes taken from published datasets rather than invented ones, and 480 rows are real. What this validates is the pipeline — feature contract, training, serving, explanation — not a real-world effect size. Proving the effect requires a real cohort, which is the stated next step.

What is Design Science Research and why did you use it?

DSR is a methodology where the research output is a designed artifact, evaluated against defined criteria — as opposed to a hypothesis tested on observational data. It fits because my contribution is the instrument: a working system that measures parental attention objectively. I build it, then evaluate it. A purely empirical methodology would have required the real cohort I don't have.

14.2 On the machine learning

How many models did you train?

Exactly one shipped: the Random Forest. Two more — Logistic Regression and Gradient Boosting — were trained purely as benchmarks. MediaPipe is pre-trained and used as-is. The PEI is a formula, not a model.

Why Random Forest and not deep learning?

Two reasons. Tree ensembles beat neural networks on tabular data of this size — 1,680 rows would badly overfit a network. And explainability is the point: the feature importances are my parental-factor argument. A black box would defeat the research purpose.

Explain how a Random Forest works.

A single decision tree asks a chain of yes/no threshold questions and overfits its training data. A Random Forest trains 300 trees, each on a random bootstrap sample of rows and considering a random subset of features at each split, then takes a majority vote. The randomness decorrelates their errors so they cancel — that's bagging. Counting how much each feature reduced impurity across all 300 trees gives feature importances for free.

Is 74.5% accuracy good?

On three classes, chance is ~33%, so 0.745 accuracy and 0.752 macro-F1 is a solid, balanced result. Macro-F1 matters more than accuracy here because it weights all three bands equally regardless of class size. But it's on simulated plus xAPI data, so it validates the pipeline, not a real-world effect.

Why macro-F1 rather than accuracy?

Accuracy hides poor performance on a minority band — always predicting the majority class would still score reasonably. Macro-F1 averages per-class F1 equally, so failing on "high risk" is penalised properly. Missing a genuinely at-risk student is the costly error here.

What's the difference between precision and recall in your context?

Precision on the high-risk class: of the students I flagged as high risk, how many really were — low precision wastes staff time. Recall: of the genuinely high-risk students, how many did I catch — low recall means children slip through. Recall matters more for the intervention use-case, which is why I report macro-F1 rather than accuracy alone.

Did Random Forest actually beat the others?

No, and I'm explicit. Gradient Boosting has slightly better test F1 (0.7540 vs 0.7521); Logistic Regression has better cross-validated F1 (0.7504 vs 0.7281) and is the most stable. All three within 1.4 points. I selected on explainability, and my training script encodes that — it only overrides Random Forest if a challenger beats it on CV F1 by more than 0.03.

Why is your CV F1 lower than your test F1?

The test score comes from one particular 25% split; the CV mean averages five folds and is the more trustworthy estimate. A gap of ~0.024 against a standard deviation of 0.037 means the test split was slightly favourable — normal variance, not overfitting.

How do you prevent overfitting?

Bagging across 300 trees on bootstrap samples; a stratified held-out test set never seen during fitting; and 5-fold cross-validation reported alongside. I didn't cap max_depth — with 300 trees, ensemble averaging controls variance, and the CV standard deviation of 0.037 confirms it isn't memorising.

Why 300 trees? Why not 100 or 1000?

Random Forest performance plateaus as trees increase — more trees never hurt accuracy, only training time. 300 is comfortably past the plateau for 9 features and 1,680 rows while still training in seconds. Below ~100 the importances start to jitter between runs, which would undermine the explanation stability I depend on.

Why no feature scaling?

Trees split on thresholds within a single feature, so monotonic rescaling changes nothing. Only the Logistic Regression benchmark is wrapped with a StandardScaler, so it competes fairly rather than being hobbled.

What is random_state=42 for?

Reproducibility. It fixes the bootstrap sampling, feature subsampling and the train/test split, so the same data produces the same model and the same reported metrics on any machine.

Why stratified splitting?

It preserves the proportion of low/medium/high in both train and test. Without it, a random split could under-represent the high-risk band in training, and the test metrics for that class would be computed on very few rows — unstable and misleading.

Why not use XGBoost?

scikit-learn's GradientBoostingClassifier is the same family and was benchmarked — it didn't meaningfully win. Adding XGBoost would introduce a heavier dependency to chase a difference smaller than the noise floor. At 100× the data it would be the first thing I'd try.

Why classification rather than regression?

The intervention is categorical — staff triage into "watch this one" buckets, not "predicted score 61.4". Three ordered bands match how the output is used, make the confidence figure meaningful via predict_proba, and let me weight the asymmetric cost of missing a high-risk student through macro-F1.

14.3 On prediction and explanation

Walk me through one prediction.

Four queries assemble the nine features for that child; missing values default to 0 except attention which defaults to 0.5; the vector is built as a named DataFrame in the frozen feature order; predict_proba returns three probabilities; the highest becomes the band and its probability the confidence; the top four features by importance are annotated against population midpoints; the result is written to predictions and, if the band worsened, a risk_alert fires to linked parents.

What does risk_score mean?

The model's confidence in the predicted class, not a danger magnitude. Low risk with 0.92 means 92% confident the student is low risk.

How does the model explain itself?

Top four features by global importance, each compared to a population midpoint and phrased as "raises" or "lowers" risk with the student's own value. I'm transparent that these are global rankings, not per-child SHAP attributions — the same four appear for everyone, only the values personalise. SHAP is the natural next step.

Why does the feature order need to be frozen?

The model is fitted on positional columns. If serving built the vector in a different order, every prediction would be silently wrong — no error, just nonsense. So the order lives in one file used by both training and serving, and is written into the model's metadata sidecar; serving rebuilds a named DataFrame from that stored order.

What happens to a brand-new student with no data?

Every behavioural feature is 0, pushing them toward high risk. That's the correct default — an invisible student is a concern, not a safe one — but it should be read as "insufficient data" rather than a genuine assessment.

How often does the model retrain?

It doesn't retrain automatically — training is an offline script run deliberately, and the artifact is versioned as predictor_v1. That's intentional: a model that silently retrains on production data can drift without anyone noticing, and for a system making risk judgements about children, the model in use should be a known, auditable artifact.

14.4 On the camera

Isn't a camera on a parent an ethics problem?

I designed for it. All processing is in-browser; only a number and a duration are stored; no frame leaves the device. There's an explicit consent gate, a visible on-air indicator and a liveness check. Real data collection would require formal ethics-committee review given minors and a webcam.

How do you stop a parent gaming the timer?

Four defences. Liveness confirms a live person rather than a photo. Tab-switching counts as inattentive. Frame gaps are capped at 500 ms so a stalled tab can't inflate totals. And at least 3 minutes of genuine tracking must accrue before Stop enables.

How do you know they're looking at the screen and not past it?

A two-condition heuristic: iris centred within 0.23 horizontally and 0.30 vertically in both eyes, and head yaw within 0.16 of forward. Both must hold. I'm honest that it's a heuristic — true gaze estimation needs per-device calibration, so I treat the output as indicative.

Why not train your own attention model?

No parent-attention dataset exists. Fine-tuning would need labelled gaze data, a GPU and weeks. And MediaPipe runs in-browser, which is the entire privacy argument — training my own would mean shipping video to a server.

What if the parent has no webcam?

Monitoring continues on behaviour alone with the 0.5 neutral placeholder. The attention_scores table existed from day one, so no schema change was needed.

How do you know it's the parent and not someone else?

I don't verify identity, and that's deliberate. Face matching would mean storing biometric PII — a serious escalation in both ethics and data-protection obligation. Liveness confirms a real person is present, which is sufficient for the research claim: that attention can be measured objectively rather than self-reported. Identity verification is a separate problem I explicitly scoped out.

14.5 On the system

How do you stop one family reading another's data?

Every table has RLS enabled; sensitive tables have no client-read policy at all, so they're reachable only through my API. The API enforces two independent layers: a role guard, and an ownership check verifying a parent_child_link row for that exact child. Role alone is never sufficient.

Why enable RLS but not write policies?

Defence in depth. RLS on with no policy means a leaked anon key still reads nothing. The rules this system needs — link-based, column-aware, state-dependent — can't be expressed cleanly in SQL policies, and splitting them across two places would create two sources of truth that drift.

Why read the role from the database rather than the JWT?

The token proves identity; the database is the source of truth for permissions. Revoking a role takes effect on the next request instead of when the token expires.

Why doesn't the child see their risk score?

A "high risk" label is self-fulfilling for a teenager. Risk is visible only to admins and parents, always in supportive language. It's an ethical design choice, not a technical limitation.

Why FastAPI rather than Django or Flask?

Native async, Pydantic type validation at the boundary, and auto-generated OpenAPI docs. Django's ORM and admin would be dead weight since Supabase is the database layer, and Flask would mean assembling validation and docs by hand.

Why Supabase rather than Firebase?

Firebase is NoSQL, a poor fit for inherently relational data — students, parents, links, quizzes, attempts. Supabase gives real Postgres with foreign keys and constraints, plus Auth, Storage and RLS in one product, and its JWT model works cleanly with server-side role checks.

How did you test this?

pytest against an in-memory fake Supabase client that reproduces the query-builder surface the code uses, so tests are deterministic and fast — currently 44 passing, including authorization tests proving a child gets 403 on a subject they don't take. Frontend correctness is enforced by tsc. I'm clear on the boundary: these test my logic, not schema drift.

How do you know the tests are meaningful if they don't hit a real database?

They test my logic — authorization, filtering, grading — deterministically. I'm explicit that they cannot catch schema drift: a missing migration passes every test and fails immediately in the browser. That's exactly why applying migrations is a documented deployment step rather than something assumed.

What would you do next?

Retrain on a real consented cohort; a real-device gaze-calibration pass; per-child SHAP explanations; and, ethics permitting, fold the real camera attention signal into training rather than the 0.5 placeholder.

17The hard questions

The ones designed to find whether you understand your own work. Prepare these above all else.

Your most important feature is prior academic score at 0.218. Doesn't that mean your model just predicts that past grades predict future grades — which is trivially known?

Partly, and that's expected: prior attainment is the strongest predictor in essentially all of the educational-data-mining literature, so a model that didn't find it would be suspect. It's a sanity check that the pipeline works. The interesting result is what sits alongside it — the three parental features together carry 0.223, marginally more than prior grades alone, and they're actionable in a way past grades are not. You cannot change a student's history; you can change how a parent engages this term.

Your camera feature is the least important at 0.059. Doesn't that undermine your entire thesis?

It's the fairest challenge available, and the answer is that the number is an artifact of how the feature had to be constructed, not a finding about the real signal. Be precise here, because a careless version of this answer is checkable and wrong: the feature is not simply constant. In the 1,200 simulated rows it varies; it is constant at 0.5 only in the 480 recast xAPI rows. Three things suppress its importance. First, compressed variance — in simulation it spans about 0.325–0.675 while prior_avg_score spans 35–90, and trees split on thresholds, so a narrow range offers fewer discriminating cut-points. Second, it is constant across 28.6% of the data, contributing nothing there. Third, it is drawn from the same latent factor as the stronger features, and under correlated inputs tree ensembles attribute importance to whichever feature splits most cleanly — classic importance dilution. The telling detail: I assigned it weight 0.10 in the label formula, fifth of nine, yet it recovers as last at 0.0586. That gap between designed weight and recovered importance is the result — with a low-variance, partly-constant proxy the signal cannot be recovered, which is exactly the argument for collecting real camera data. Reading 0.0586 as "the camera doesn't matter" would misread my own experiment. See section 7.7.

If the PEI feeds the predictor, and reading a risk alert raises the PEI, haven't you built a circular system?

There is a feedback loop, and it's deliberate rather than accidental: parental responsiveness flows back into the next prediction without retraining. It isn't circular in the invalidating sense, because the loop passes through real-world behaviour — a parent must actually open the notification. But it does mean PEI and risk are not independent over time, so a longitudinal study would need to account for it. It's a limitation of the deployed feedback design, not of the model.

Your three models are within 1.4%. Isn't that just saying your features are weak and the algorithm doesn't matter?

It says the signal is in the features, not the algorithm — which is the normal finding on well-constructed tabular problems and is genuinely informative. When three model families with very different inductive biases converge, the ceiling is being set by the information in the features. That strengthens rather than weakens the case for choosing on explainability, since accuracy isn't being sacrificed to get it. It also tells me where to invest next: better features, or real data — not a fancier algorithm.

You said 18 tables but one is unused. Is that not dead code?

messages was created up-front as part of a deliberate strategy: later-phase tables were included in the initial schema so no phase needed a mid-project migration. That paid off for attention_scores, which meant the Phase 7 camera needed no schema change at all. messages is the case where the feature was descoped. An empty table costs nothing, whereas a migration mid-project costs a lot — but it's fair to call it a loose end.

How would you validate that camera-measured attention beats self-reported involvement — your central claim?

I'd need both measures on the same cohort: a standard parental-involvement self-report questionnaire, the camera measurement, and student outcomes over a term. The test is which measure correlates more strongly with outcomes, and whether the camera measure adds predictive power over the questionnaire in a nested model comparison. I'd also quantify self-report bias directly by comparing what parents claim against what was measured. That study isn't in this project's scope — this project builds the instrument that would make it possible.

A parent could just sit in front of the camera and scroll their phone. Your system would record full attention.

Correct, and that's a real limitation of gaze-only measurement. My defences catch absence and inattention — looking away, turning the head, leaving the tab, propping up a photo — but not a person physically facing the screen while mentally disengaged. Detecting genuine cognitive engagement would need a different modality: expression analysis, or correlating attention with interaction events like scrolling and clicking. That correlation is actually the cheapest next step, since I already log both.

Why should a school trust a model trained on data you invented?

It shouldn't, and I wouldn't ask it to. The deployable claim is narrower: this is a working, explainable pipeline whose predictions are auditable factor by factor, validated end to end on data with realistic structure. Before any school acted on a prediction, the model would need retraining on that school's real, consented cohort — the code path for that is exactly the same script. What I'm defending is the method and the instrument, not this specific set of weights.
