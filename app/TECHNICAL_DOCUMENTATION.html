1Executive summary

This is a role-based Learning Management System (LMS) for Sri Lankan O/L (Ordinary Level) students, built to study how parental involvement relates to student performance — and, crucially, to introduce a new way of measuring that involvement.

RoleWhat they do
AdminProvisions all accounts, uploads materials, builds & grades quizzes, uploads report cards, runs risk predictions.
ParentMonitors their linked child's activity, engagement & results; opts into camera attention verification; receives notifications; views report cards.
ChildStudies materials and takes quizzes. Never sees a risk prediction (an ethical choice).

Two intelligence layers sit on the LMS: (1) an explainable Random Forest risk predictor (low / medium / high, with reasons), and (2) a transparent Parental Engagement Index (PEI) formula.

The novelty

The camera points at the parent, not the student: it objectively verifies that a parent is genuinely attending to their child's progress, replacing unreliable self-reports.

2Research positioning (the thesis)

2.1 The research gap and novelty

The parental-involvement→performance link is already established in the literature — claiming to discover it would be a mistake. The genuine contribution is methodological: objective, camera-verified measurement of parental attention instead of self-reports. Every existing attention study points the camera at the student; no existing work points it at the parent. This applies Multimodal Learning Analytics (MMLA) to a new subject.

2.2 Field vs methodology

  • Field: Learning Analytics → Educational Data Mining → Multimodal Learning Analytics (behavioural logs + camera data).
  • Methodology: Design Science Research (DSR) — build an artifact, then evaluate it.

2.3 Association, not causation

Because the training data is simulated, the project demonstrates the method and pipeline, not a proven effect size. All results are framed as association / prediction, never causation — stated openly as a clear, honest scope.

2.4 Ethical stance

  • Privacy-first camera: video is processed in the browser; only the attention number + duration is stored — no raw frames leave the device.
  • Minors + webcam: real data collection would require a formal ethics-committee review.
  • No self-fulfilling labels: the child never sees their own risk score.
  • Support, not blame: supportive language in all parent-facing risk copy.

3System architecture

A single-page React app talks to two backends. Supabase provides auth (issues the JWT), the profiles table, and file storage. FastAPI owns all business logic and all authorization, talking to the database with the service-role key (which bypasses RLS). The Supabase JWT bridges the two.

Backend layering (3 tiers)

Routers (HTTP surface: role guards, ownership checks) → Services / ML (domain logic, the predictor, the PEI) → DB client (one accessor, get_service_client()). Every request: CORS → route → auth dependency (decode JWT + load profile) → role/ownership guard → service-role query → optional service/ML call → JSON.

5.3 Row-Level Security — the "golden rule"

RLS-vs-API golden rule

RLS is enabled on all 16 tables (nothing is world-readable by default), but all role/ownership authorization runs in FastAPI using the service-role client, which bypasses RLS. A few simple reads (own profile; own links; authenticated reads of subjects/materials/quizzes) have policies and go direct to Supabase. Everything sensitive has RLS on but no policies — reachable only through the API, which applies its own checks.

A SECURITY DEFINER trigger creates each profiles row after signup, avoiding a client-insert race against RLS. Storage buckets materials and report-cards are both private; downloads use time-limited signed URLs.

6Backend & API

6.1 Authorization (role + ownership)

Two layers: a role guard (require_role("admin") → 403 if disallowed) and an ownership check (a parent endpoint verifies a parent_child_link row for that exact child → 403 "Not linked to this child"). Role alone is never sufficient.

6.2 Authentication

The browser sends Authorization: Bearer <supabase-jwt>. The token is verified via Supabase's JWKS endpoint with asymmetric keys (ES256/RS256), audience="authenticated", leeway=10s. The user's role is read from the profiles table, not the JWT — the token authenticates identity; the DB is the source of truth for role.

6.4 Notifications service

Four event types — quiz_result, quiz_due, report_card, risk_alert — fanned out to all linked parents, created only by the backend. quiz_due reminders are generated lazily (no cron) with dedup; notify_safe ensures a notification failure never fails the underlying action; and reading a notification raises the PEI via check_frequency — no new ML feature, no retrain.

One-line summary for the viva

"One trained model (the explainable Random Forest risk predictor), selected after benchmarking two alternatives; one pre-trained model used as-is (MediaPipe, for the camera); and one transparent rule-based scorer (the PEI, which is not machine learning). An attention-quality classifier was scoped but deliberately dropped." A lean, explainable strategy beats a stack of black boxes — and the camera task correctly reuses a proven pre-trained model rather than training one from scratch.

7.1 The predictor model

AlgorithmRandomForestClassifier (scikit-learn) — the committed production model
Hyperparametersn_estimators=300, max_depth=None, random_state=42

Two benchmarks were also trained: Logistic Regression (scaled) and Gradient Boosting.

7.3 Why Random Forest (explainability over raw accuracy)

  1. Tree ensembles beat neural networks on tabular data.
  2. Explainability is the point — the feature importances are the parental-factor argument; a black box would defeat the research purpose.
Honest note for the viva

On the held-out set, Gradient Boosting is marginally ahead and Logistic Regression has the best CV macro-F1 — all three are within ~1%. RF was chosen for explainability, not because it dominated every metric. That transparency is itself defensible.

7.5 Training data generation (simulation)

Why simulate? No public dataset ships in the exact feature schema. So public datasets are mined for documented relationships, which are then reproduced in a simulated Sri Lankan O/L dataset in that schema.

  • xAPI-Edu-Data (480 rows) — primary grounding, carries parental fields (e.g. survey Yes→1.32 vs No→0.66; absences under-7→1.44 vs above-7→0.41).
  • UCI Student Performance — family-context features.
  • OULAD — large behavioural reference (optional).

Procedure (seed 42): a latent "engaged household + able student" factor drives correlated features; a weighted success score (weights echo the literature — prior grades 0.24, quiz avg 0.20, attendance 0.15, parental ~0.30 combined) + noise maps to a risk band (≥0.60 low, ≥0.42 medium, else high). Every row is tagged data_source for transparency; 480 real xAPI rows are recast into the schema.

7.6 The Parental Engagement Index (a formula, not ML)

PEI = 0.4 · norm(monitoring_hours)   (cap 10 h)
    + 0.3 · norm(check_frequency)    (cap 25)
    + 0.3 · parental_attention       (0.5 placeholder until the camera)

check_frequency = history-checks + notifications the parent has read. The normalisation caps match the training-data caps, so a runtime PEI is comparable to the features the model trained on. The engagement_index table is both a product surface and the predictor's parental-feature source.

7.7 Serving & explanations

The model + meta load once and cache. A prediction rebuilds the vector in the frozen order as a named-column DataFrame, then predict_proba gives the band + confidence. Explanations take the top-4 features by global importance, compared to a population midpoint, as "raises/lowers risk" lines with the child's value.

Honest nuance

These are global importance rankings, not per-child SHAP attributions — the same 4 factors appear for every child; only the values/direction personalise. SHAP is the natural next step.

7.8 The feedback loop

Reading a risk alert raises check_frequency → raises the PEI → feeds the predictor's parental features on the next run. Parental responsiveness thus flows back into the model — without changing the model itself.

8The camera attention feature (the novelty)

Phase 7 · scope A+E (attention verification + liveness), supervisor-approved. The camera points at the parent, entirely in the browser.

Pipeline

  1. Consent gate — explains on-device processing, no video stored, liveness, on-air indicator, 3-minute minimum. Nothing starts until accepted.
  2. Face landmarking — MediaPipe's pre-trained 478-point FaceLandmarker at ~8 fps on a hidden self-view (used as-is).
  3. Liveness first (the "E") — confirms a real person via blink OR head motion; 8s timeout → retryable failure.
  4. Eyes-on-screen heuristic — attentive only if iris is centred in both eyes AND head faces forward.
  5. Accumulation + debounce — a 1.5s grace window means a blink doesn't drop the count; capped frame gaps stop stalls inflating totals.
  6. Anti-gaming — switching tabs counts as inattentive.
  7. Minimum-time lock — genuine tracking must accrue ≥3 minutes before Stop enables (with a live countdown).
  8. Result POST — only {attentive_seconds, total_seconds, liveness_passed} is sent. No video/frames ever leave the browser.
Privacy & testability by design

The gaze/liveness/accumulation logic is pure functions (unit-testable with fixtures), and a mock tracker enables full end-to-end flow testing without a real webcam. Camera denied/absent → graceful behaviour-only monitoring with the 0.5 attention placeholder (no schema change — the "socket" pre-existed).

11Key engineering decisions & why

  • Thread-local Supabase client — per-thread reuse (avoids ~220ms rebuilds) without sharing an HTTP pool across threadpool threads, which caused intermittent disconnects.
  • "Phantom CORS" fix — Starlette's default 500 is generated outside the CORS middleware, so the browser misreports it; a global handler keeps the CORS header, and missing-file errors become clean 404s with actionable messages.
  • Lazy notification generation — no cron; quiz_due reminders generated on demand with dedup.
  • Manual upsert-by-key — predictions & engagement index upserted by hand where no unique constraint exists.
  • notify_safe everywhere — a notification failure never fails the core action.
  • Answer-key stripping for children; short-answer notification deferred until fully graded.

12Limitations & honest scope

  1. Trained on simulated data — accuracy (~74.5%) and explanations reflect simulated relationships; association, not causation; real deployment needs a consented real cohort.
  2. Camera needs real-device calibration — gaze thresholds tuned on controlled input; treat attention % as indicative.
  3. PEI is a formula, not ML — reflects chosen weights, by design.
  4. Explanations are global-importance rankings, not per-child SHAP.
  5. parental_attention is a 0.5 placeholder in training and the least-important feature — the real signal is new.
  6. Scope: one trained model + one pre-trained (MediaPipe) + one rule-based scorer; no self-signup; no email/SMS/push; parent face-matching deliberately not built (biometric PII + ethics; liveness suffices).

13Anticipated viva questions & answers

Q: What is your actual research contribution?

Objective, camera-verified measurement of parental attention. The involvement→performance link is established; my contribution applies Multimodal Learning Analytics to a new subject — the parent — replacing self-reports with an on-device attention measurement.

Q: Why simulated data? Isn't that a weakness?

No public dataset holds that exact feature combination per O/L student. I mined public datasets (xAPI, UCI) for the documented relationships and reproduced them in my schema, plus recast 480 real xAPI rows. I demonstrate the method and pipeline; every result is framed as association, not causation; every row is tagged with its data_source.

Q: Why Random Forest, not deep learning?

Tree ensembles beat neural networks on tabular data, and — decisively — explainability: the feature importances are my argument. I benchmarked Logistic Regression and Gradient Boosting; they're within ~1%, and I kept RF for explainability, not dominance. That honesty is defensible.

Q: Is ~75% accuracy good?

On three classes, chance is ~33%, so 0.75 accuracy / 0.752 macro-F1 is a solid, balanced result — but it's on simulated + xAPI data, so it validates the pipeline, not a real-world effect size.

Q: How does the model explain itself?

Top-4 features by global importance, compared to a population midpoint, as plain-language "raises/lowers risk" lines with the child's value. I'm transparent these are global rankings, not per-child SHAP — a clear next step.

Q: How do you protect one family's data from another?

Every table has RLS enabled; sensitive tables have no client-read policies, so they're reachable only through my API, which enforces role and ownership — a parent endpoint always verifies a parent_child_link row for that child, else 403.

Q: Isn't a camera on a parent an ethics problem?

I designed for it: all processing is in-browser; only a number + duration is stored — no video leaves the device. There's a consent gate, a visible on-air indicator, and a liveness check. Real data collection would require a formal ethics-committee review, given minors and a webcam.

Q: How do you stop the parent gaming the attention timer?

A liveness check confirms a real person; switching tabs counts as inattentive; frame-gap caps stop a stalled tab inflating totals; and a 3-minute minimum must accrue before stopping.

Q: Why doesn't the child see their risk score?

A "high risk" label can be self-fulfilling for a teenager. Risk is visible only to admins and parents, always in supportive language.

Q: What would you do next?

Retrain on a real consented cohort; a real-device gaze-calibration pass; per-child SHAP explanations; and (ethics permitting) fold the real camera attention signal into training rather than the 0.5 placeholder.
